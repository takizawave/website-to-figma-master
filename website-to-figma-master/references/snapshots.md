# 月次snapshot

## 目的と保存時点

ユーザーが過去の画面を月単位で比較できるようにする。変更が無い月も保存する。snapshotは保存時点のFigma masterの状態であり、Webサイトをその時点で再取得した結果とは区別する。

- 初回：master完成後に、当月の基準snapshotを作る。
- 定期：毎月1日09:00を既定に、ユーザーのタイムゾーンで1回保存する。既に指定された日付・時刻・タイムゾーンを優先する。既定を使う場合は設定時に伝える。
- 更新前：当月分がまだ無ければ、masterを書き換える前に保存する。当月分があればそのまま保持する。その後の変更前後は04 更新履歴に残す。
- スケジュールの実行が遅れた場合：実際に保存した日時を明記する。存在しない過去月の画面を、現在の画面から捏造しない。

「月1回」はカレンダー月単位。1か月の秒数を固定したタイマーで代用しない。タイムゾーンは会話または実行環境のユーザー設定から確定し、不明な場合だけ確認する。

## 保存範囲

対象プロジェクトのScreens全体（作成済みのdesktop/mobile、観察済みの状態）、それらのComponents、Foundationsを保存する。元サイトに無い画面や対象外のページは追加しない。

`05 Snapshots`の中に年月別の枠を作る。例：`2026-11｜取得 2026-11-16 18:30 Asia/Tokyo`。月初に実行できなかった場合も取得日を偽らない。

枠には次を残す。

1. 各画面の固定コピーと、見た目の証拠となるPNG等の書出し。
2. コンポーネントの固定コピー、variants・propertiesの値と対応。
3. カラー・タイポグラフィ・スペーシング・角丸・影等の値、mode、元の変数・スタイルID。
4. source URL、source取得日時、snapshot取得日時、viewport、state、元masterの最終更新日時。
5. 今回の対象と欠落、保存したnode IDとasset参照、検証結果。

スクリーンショットを置く場合はSnapshotページに限定し、現行のScreensとは区別する。保存できるファイル領域があれば`snapshots/YYYY-MM/run-id/`のように書出しとmanifestもまとめる。画像や記録は実際に永続化できた場所の参照を残し、一時URLだけで保存済みとしない。

## 過去の見た目を固定する

Instanceを複製しただけでは、後のコンポーネント変更で過去も変わる。次を確認する。

- 外側・内側のInstanceを全て独立させる。snapshot内のコンポーネントコピーも現行コンポーネントへ依存させない。
- 各ノードの実効値を保存してから変数のbindingと共通styleへの参照を切る。文字のrange単位のstyle、component property、modeの影響も確認する。
- 元の画面と固定コピーを書き出して比較する。書出し画像を独立した証拠として保持する。
- PNGのファイル内容が異なっても圧縮やmetadataの差だけの場合がある。画像をデコードした画素の一致と、ファイルのバイト一致を区別する。
- 初回は代表画面で、元の色・コンポーネントを一時変更して固定コピーが変わらないことを確認する。検証用変更は必ず戻す。空のTextに文字range用APIを呼ぶ前には、文字数を確認する。
- APIの制約で完全な固定コピーが作れなければ、PNGと値のmanifestを必須の代替とする。「固定コピー未作成、画像と値を保存」と明記する。

将来のフォント環境等で編集レイヤーの表示が変わり得るため、画像の証拠も残す。保存した画像まで現行のnode書出しURLへ動的にリンクする形にしない。

## 再実行と保持

snapshotキーは`projectId + fileKey + YYYY-MM`。記録とFigma双方で存在を確認する。完了済みなら重複保存せず、その月のリンクを返す。

途中失敗の場合はstatusをpartialとし、同じsnapshot枠の不足分だけを補う。保存・検証できたものだけcompleteにする。手動実行と定期実行が重なったら、書込み前に既存の実行状態を確認し、同じ月への二重書込みを避ける。ロック機能がなければ重なった実行は進めず、進行中の実行結果を確認する。

過去分は無期限保持を既定にし、自動削除・上書きをしない。ファイルが重くなり分割が必要になったら、移動先と参照維持の案を作り、ユーザーと決めてから移す。

## 定期実行の設定

スキルの導入だけでは毎月は実行されない。初回のmaster作成後、以下を整える。

1. 設定とstateが将来の実行から読める永続的な場所にある。
2. スケジューラがFigmaの対象ファイルと書込み・書出し機能を使える。
3. 対象ファイル、プロジェクト、タイムゾーン、実行時刻が確定している。
4. 同じ対象の既存タスクを確認し、あれば更新し、重複を作らない。

環境にタスク・自動実行機能があれば、その正式な機能で月次実行を登録する。ユーザーの「毎月snapshotを残す」という依頼の範囲で設定し、既に得た許可を繰り返し求めない。ただし保存先や外部接続の追加が必要なら、その不足分を解消する。

実行指示にはこの内容を含める。値は確定済みの実値で埋める。

> website-to-figma-masterのsnapshot-onlyモードで、指定されたプロジェクトとFigmaファイルの当月snapshotを保存する。永続化された設定・stateを読み、同月の完了分があれば重複作成しない。Web再取得やmasterの更新は行わない。画面・コンポーネント・スタイルの現在値を固定し、画像を保存して照合する。実取得日時と元masterの最終更新日時を記録する。完了リンク、欠落、失敗を報告する。

登録後、返されたtask ID、実際のスケジュール、必要なアクセス条件を記録する。スケジューラの登録と、snapshotが実際に保存されたことを区別する。通知やリマインダーしか使えない機能を、自動保存タスクと説明しない。

定期実行機能が無い場合は`not-configured`を記録し、上の依頼文と次回予定日を渡す。更新時に当月分を保存する処理は継続するが、それだけで操作しない月まで保存できるとは説明しない。
